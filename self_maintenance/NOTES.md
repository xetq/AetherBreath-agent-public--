### 13.2 六个 bug：只有真浏览器（和**目视截图**）能抓到

`tsc --noEmit` 全绿、`vite build` 成功 —— 然后第一次真机验收 **14/22**。抓到的：

1. **hook 自己新造了一个 ref，而不是用真的滚动容器**（最隐蔽）。
   `useMsgNav` 内部 `const scRef = useRef()` 从未挂到任何 DOM 上 ⇒ `sync`/`jump` 全在
   `scRef.current === null` 上提前返回。表现极具误导性：**竖轨画得整整齐齐、点了没反应**
   （因为画竖轨用的是组件收到的那份 `box`，走的另一条路）。
   修法：ref 由**调用方传入**（`useMsgNav(scrollRef, …)`），一个容器一个真相。
   **教训：hook 里"再 ref 一次"看起来无害，实际等于换了个人问路。**

2. **预览框被轨道自己的 `overflow-y: auto` 裁掉**。轨道消息多时要能滚，
   而 CSS 里"一个轴 visible + 另一个轴 auto"会被规范强制成 `auto` ⇒ 预览框整个落在
   轨道左侧，**必被裁**（调 z-index 救不了）。实测证据：`x=-277`（跑到视口外）。
   修法：预览框**渲染在轨道之外**（挂到滚动容器的 fixed 层），并且**不用 offsetParent
   那套**（被 `document.body` 接住时 `left:-277` 直接飞出屏），一律用
   `getBoundingClientRect()` 的**视口坐标** + 上下左右夹紧。

3. **锚点用"第几个回合"，而"第几个回合"有两种解释**。历史按 `limit=400` 条截断
   （`sessions.py:300` 的 `out[-limit:]`），被截断的会话里
   "回合序号" ≠ "消息流下标" ≠ sidecar 的 `user_seq`。修法：`TurnView.anchor` =
   用户消息在原始消息流里的下标，锚点/导航/跳转全都只用它。实测该会话 99 条用户消息
   只渲染了 80 条 —— 界面上**没渲染的消息不该有横杠**（点了也没得跳）。

4. **高亮"到点自己消失"这件事，不能在点击后立刻判**。第一版验收脚本点完马上查
   `msg-jump-flash`，判"没消失"⇒ 假红。**1.5 秒的高亮窗口里它本来就该在**，
   要等过了窗口再查。**教训：验"定时行为"必须先跨过那个时间窗，否则测的是自己的急躁。**

5. **轨道自动滚动把整页一起滚了**（断言全绿、只有**目视截图**看出来）。
   轨道用 `dot.scrollIntoView({block:'nearest'})` 把当前条带进视野 —— 而
   `scrollIntoView` 会滚**所有**可滚动祖先，**连 document 一起滚**：
   900px 视口里整页被上顶约 70px，顶栏和轨道框都挪了位、预览框贴到窗口顶边。
   修法：只改轨道自己的 `scrollTop`（"拖到哪"按相邻两条的间距算，绝不动别人）。
   **教训：几何断言测不出"谁被滚了"这类副作用 —— 补一条"整页/顶栏/轨道框都不许动"的
   断言，外加一张目视截图。截图不是装饰，是另一种传感器。**

6. **贴顶的横杠会让预览框半截飞出屏幕**（也是目视发现的）。想"翻到横杠下方"，
   第一版判据写的是"夹紧后的 top 贴顶就翻" —— 但**轨道预滚到底时，靠前的横杠 dotTop 是负的**
   （在轨道可视区之上），于是被判成"贴顶"，翻出来的框落点 `y≈-632`，整块画在屏幕外。
   修法：判据必须看**横杠自身的可见性**（`dotTop >= 0 && dotTop < TIP_PAD + h` 才翻；
   横杠在视口下方则贴下沿）。**教训：判据要盯着"用户在看的东西"，而不是"我刚算出来的数"。**

## [2026-09-30 · P12] 交付的"呈现"与 `task_list` 的"口径"：主人两句要求，各挖出一个旧决策

主人的两句原话：

### 12.1 交付不只是"一条用户消息"，它是**卡里的一段**

P8 把交付做成了一条 `user` 消息 —— 那解决了"注入"的问题，没解决"**看得懂**"的问题：
它在界面上就是主人自己的发言样式。这次按「用户交代」的既有机制重做：

| 环节 | 做法 |
|---|---|
| 认出来 | 前端 `lib/jobDelivery.ts` 的 `JOB_DELIVERY_PREFIX` **逐字**等于 agent 侧的常量（有断言钉死，照 `midTurn.ts` 的先例） |
| 挂进卡 | 装载历史时标 `job: true` → `buildTurns` 把它挂进**所属回合** → `UserCard` 渲染（与 `mids` 并列，不单独成卡） |
| 区分开 | 交代 = 紫（人说的话）；交付 = **橙**（机器送回来的结果，同编排器那盏灯）+ 角标「✅ 全文已自动交付」；超长正文折叠 |

**"当场可见"这一环最容易漏**：交付是**落盘的消息**，实时通道里根本没有它 ——
不做处理的话，模型已经读过交付了，界面却要等你切会话/刷新才显示。
所以 agent 侧留一条回执（`take_delivered_notices`，取走即清空），bridge 放进 `done.delivered_jobs`，
store 记一个 `jobDeliveredAt`，ChatView 据此**以磁盘为准重放一次历史**。
**教训：凡是"落盘才有"的东西，都要显式给它一条"什么时候去看"的信号**，
否则它的可见性就交给了用户的耐心。

### 12.2 `task_list` 从"表"退回"仪表盘"

主人的理由很实：**运行久了表会一直占内存，而久远的作业已经写进日志/会话，留着没意义。**

- 只列**还在册**的：在跑 + 待交付。
- **交付完就出册**（`mark_delivered` = 释放内存 + `drop`），于是登记册不会越用越长。
- 连带删掉 `Job.delivered` 标记与 schema 的 `include_finished`：
  "交付过没有"现在由**"还在不在册里"**表达 —— 又一个"写了没人读"的字段退场（P6 的老教训，
  这次是**主动**清理，不是被真机打脸后才发现）。
- `task_output` 对已出册的 id 如实说"没有这个作业（可能已交付进会话历史）"并指向 `task_list`。
- 提示词同步（P11 立的规矩）：`task_list` / `task_output` 的描述都改成了新口径。

**教训：一个"表"越用越长，是设计问题，不是运维问题。** 内容已经永久落在会话里了，
登记册就该只管"现在还活着什么"。**同一份事实只留一处权威。**

## [2026-09-30 · P13] 「一起停」的真缺口不是"杀不动"，而是"没人等它落地"

主人这一项的原话（PLAN 决策 7 的落点）：**终止回合或关机 AB 全部强杀任务编排器内所有任务**。

### 先取证，别猜（这次猜错的方向很有代表性）

我原以为缺口是"杀不动"。真机取证后发现**两条路本来就是通的**：

```
停止本回合 -> bridge._stop_run -> 注入 KeyboardInterrupt -> agent.py 的 except 分支
              -> stop_all_jobs("主人点停止")        ✅
优雅关机   -> 网关 stop() -> bridge._graceful_exit -> shutdown_orchestrator()
              -> TaskOrchestrator.shutdown -> stop_all_jobs   ✅
```

而且用真进程量过：挂 `sleep 6 && echo DONE > 标记` 再 `stop_all_jobs`，
**标记确实没被写出来** —— 进程树真的被杀了。

**真正缺的是两件小事**：
1. `stop_all_jobs` 是**发完即走**（`cancel_event.set()` 之后立刻 finish + 清册），
   而工具的 poll 循环要下一拍（~50ms）才看见令牌去杀树；
2. `_graceful_exit` **紧接着 `os._exit(0)`** —— 关机链路上，没来得及杀的子进程就是孤儿。

**教训：把"信号发出去了"当成"事情办完了"，是异步系统里最常见的假成功。**
所以这次改的不是"更用力地杀"，而是**等 + 台账**。

### 做了什么

| 位置 | 改动 |
|---|---|
| `stop_all_jobs(reason, wait=2.0)` | 台账 `{total, settled, stuck}`：发信号 → **先把状态定死为 cancelled** → 有界等待 → 清册 → 写日志 |
| `shutdown(wait)` | 复用上面的台账（关机那条路的"等"就在这） |
| `agent.py` 中断分支 | 照台账说话（几个确认收手、几个没有） |
| `_launch_background` / `_run_one` | `metadata["is_background_job"]` → 给工具注入 `background_job=True` |
| `execute_shell` / `execute_python` / `win_job` | 后台作业的 Job Object 设 `KILL_ON_JOB_CLOSE`：**AB 被硬杀，内核替它收掉整棵树** |
| 前端 `agent_phase` | phase = OFF/STOPPING → `idleAll(pipes)`（关机后点阵不许还亮） |

### 两个"顺序"上的坑（都写进了判据）

1. **等谁**：一开始我等 `job.alive`，但那状态**刚被我自己改成 cancelled** ——
   循环立刻"等完"，等了个寂寞。正解是等 **`future.done()`**（工具线程真的收手）。
2. **先定状态还是先等**：支持取消令牌的工具是**协作式返回**（返回「⏹ 已被取消」这种文本），
   harvest 会把它记成 `done` —— 那不是"作业没被取消"。所以**先把状态定死**，
   后到的 harvest 那次 finish 自然成了 no-op（已结算不许被改写），状态才确定。

### 「不污染」这条红线仍然守住

`KILL_ON_JOB_CLOSE` **只对后台作业设**：后台作业的语义就是"跨回合、随时可一起停"，
AB 一死它没理由活着；而**前台**调用里用户故意后台化的活儿（`nohup server &`）
**照旧活着**（有回归门守着）。句柄只在工具调用存续期内开着，调用结束就关 ——
既不会攒句柄，也不需要额外回收线程。

## [2026-10-02 · P14] 槽位颜色污染：把"历史上发生过"当成了"此刻正发生"

主人原话：

> 若当前管道运行过"后台任务"，那么它就会被"后台任务"所对应的橙色指示灯污染，
> 以后再在这个管道运行并行任务时，就无法亮起并行任务所对应的绿色指示灯，而是橙色。

### 根因：一个**粘性槽位标记**

```ts
const place = (v) => {
  if (v.background) s.job = true     // ★ 只要这一格**历史上**出现过 background 条目就置位
}
// 渲染：const cls = on ? (s.job ? 'job' : ...) : 'idle'
```

线程会被复用 —— 同一格"先跑后台作业、后跑并行任务"是**常态**；而 store 又会把**已结束**的
后台条目留在 `pipes` 里（`idleAll` 把它落回 `idle`，却**保留** `background: true`）。
于是那次后台作业成了这一格的**永久属性**：绿色再也回不来。

## [2026-09-30 · P10] "timeout 是跑完才判"——AB 的症状对、机制错；真凶是两个进程之外的第三件事

### 现象（AB 的推理）

> 挂 `sleep 130 && echo BG130_OK`（timeout=120）→ 报「⏰ 执行超时（超过 120 秒），已强杀
> 整个进程树」，但**耗时 130.2 秒** ⇒ "timeout 并不准时强杀，而是让命令跑完再比对耗时"。

### 实测（先动手做对照实验，再信推理）

```
sleep 3                        (timeout=1) -> 1.45s 返回    ✅ 准点
sleep 5 && echo DONE > MARK.txt (timeout=1) -> 5.15s 返回    ❌ 拖满自然时长
   但 MARK.txt **不存在** -> 命令没跑完 -> 树**确实**在超时点被杀了
杀死后 2 秒的进程表：bash.exe 已消失，**sleep.exe(PID 29168) 还活着**
```

⇒ **AB 的推断不成立**（不是"跑完再判"），但它观察到的 130.2s 是真的。真凶是**第三件事**：

```
taskkill /F /T 杀掉中间那层 shell
  -> 真正干活的孙进程被**重新挂靠**、逃出 /T 的遍历，继续运行
  -> 它还持有 stdout/stderr 管道
  -> 读线程卡在 read()
  -> 收尾的 finally 里 pipe.close() 在等读线程的锁   ← ★ 卡在这里
  -> 工具要等那条命令**自然结束**才返回（sleep 130 -> 130.2s）
```

### 教训

1. **超时"不准时"要分成三段查：判定点、杀点、返回点。** 这次判定与杀点都准，
   只有**返回点**被拖住了 —— 而"看起来"完全是"没杀/没超时"。
2. **纯 sleep 不触发、`&&`/`|` 才触发** —— 差异不在超时逻辑，在**进程树形状**（多一层 shell
   才有"被重新挂靠的孙进程"）。**我的对照实验必须覆盖两种命令形状**，只测一种就会得出
    AB 那个错误结论。
3. **`close()` 不是无害的收尾动作。** 对"另一个线程正卡在 read()"的管道调 `close()`，
   会等那把锁 —— 于是"关管道防 fd 泄漏"（审计 B21）变成了"把工具钉在命令的自然结束上"。
   **任何可能阻塞的清理动作，都必须搬到主路径之外。**
4. **被静默吞掉的边界要摆到台面上。** `taskkill /T` 漏孙进程这件事一直存在，
   但因为没人说，它就伪装成了"超时不准"。现在工具会**如实提示**"可能有子进程逃过强杀"。

### 做了什么（两个工具同改，判据共用）

| 文件 | 改动 |
|---|---|
| `agent_tools/execute_shell.py` | `_close_pipes_nonblocking()` + `_defer_pipe_cleanup()`：读线程没结束就把"等它 + 关管道"交给 daemon 回收线程；被杀路径**不再 join 读线程**；`_orphan_note()`：读线程仍卡着 = 有孙进程逃过强杀 -> **如实写进返回值**；`_kill_process_tree` 的 docstring 记下这个已知边界 |

## [2026-09-30 · P9] 杀掉作业后灯不灭：我把"登记册里没有"当成了"看不见"

### 现象（主人原话）

> `task_kill` 掉后台任务的时候，确实不再跑了，但是任务编排器没有随之暗下来。

### 根因（一处判断，两个方向都错）

```python

if job is not None:
    if not job.alive: continue        # 已结算 -> 出局
    ...
out.append(v)                         # ← job 为 None 时**原样上报 running**
```

`task_kill` 的最后一件事是 `reg.drop(jid)`（把作业从登记册**移除**），而那个作业的工具线程
还在自己的取消令牌上收尾（它可能还要跑一会儿）。于是 `_PIPES` 里那条 `background/running`
条目**永远等不到终结**，而 `/orch` 视图查不到作业时按"fail-open"原样上报 `running` ——
**前端每 5 秒对一次表，反而把橙灯一次次维持住**。进程确实停了，灯却一直亮。

**P5 为什么这么写**：当时防的是"登记册**读不到**时把可能还在跑的作业判成不存在"。
但"读不到"（`_agent` 还没装好）与"读到了、里面没有"（作业**确实没了**）是两件事 ——
我把它们混成了一个分支。**"看不见"与"不存在"必须分开判。**

### 教训

1. **"查不到"要分两种**：拿不到权威来源（fail-open）vs 权威来源明确说没有（fail-closed）。
   混在一起，就是这次：杀掉的作业被当成"可能还在跑"。
2. **drop 掉的东西，别指望别处替它收尾。** `_PIPES` 里的条目靠"工具线程跑完发终态帧"清理；
   作业被 drop 之后，那条链就断了 —— **谁做的删除，谁负责让下游看见**。这次补了
   `_sweep_dead_background_pipes()`：以登记册为准，把死占用**发终态帧 + 出局**。
3. **对表机制会把错误"维持"下去。** 前端的 5 秒对表本来是止血用的，却因为服务端视图错，
   变成了"每 5 秒再点一次灯"。**自愈通道的正确性比它本身更重要** —— 它错了就是放大器。

### 做了什么（只动 bridge 一个文件）

## [2026-09-29 · P5] 橙灯为什么"回复后就灭"：我把跨回合作业当成了回合内的东西

### 现象（主人原话）

> 前端任务编排器点阵在挂载后台任务的时候，应当亮起橙色指示。我让 AB「挂一个 30 秒的任务

### 根因（三个断点，每一个都让橙点失真）

| # | 断点 | 为什么它让灯灭 |
|---|---|---|
| 1 | 前端 `appStore.idleAll()` 对**所有**管道置 `idle`，而 `done` 分支正是调它 | 回合收尾 = 所有格子转空闲 —— 跨回合作业也被一起抹了 |

### 教训

1. **"跨回合"是语义，不是时长。** 作业的定义就是"活过它出生的那个回合"，

## [2026-09-29 · P4] busy 卡死的实证根因：后台作业收尾的那一帧 `turn_phase`（前几轮猜错了方向）

### 现象（主人原话）

我把"延迟绑定"的 `_JobLogger` 套到了**所有**调用上（包括前台），而它只实现了
`info/warning/error/debug`。`SessionLogger` 还有 `span/child` 之类的接口 ——

  它报「编排器按签名注入 logger（span=mcp:*）：0 条 mcp 事件」。

  ② 包装加 `__getattr__` 转发。

### 1) test_stderr_flood_does_not_block_the_call ——【真实产品缺陷】
- **机制**：`mcp_client._write_locked` 用 `json.dumps(payload, ensure_ascii=False)` 把
  **UTF-8 字节**写进子进程 stdin；但 `_spawn_locked` 只做 `os.environ.copy()`，
  **不保证子进程按 UTF-8 读 stdin**。Windows 中文环境下 Python 子进程默认 cp936，
  于是 `tests/mcp_stub_server.py` 的 `for line in sys.stdin:` 把中文 payload 解成
  孤立代理字符（U+DCAA 形态）→ server 写日志时
  `UnicodeEncodeError: surrogates not allowed` → **进程崩（rc=1）** → 客户端读到 EOF。
- **为什么容易查错**：报错文案是"server 输出已关闭（读到 EOF）—— 进程很可能已退出"，
  字面指向"进程退出/stderr"，**与 flood 本身无关**，真凶是**中文 payload + 编码**。
- **双向证据**（同一命令，只改环境变量）：
  无变量 → `1 failed, 29 passed`；`PYTHONUTF8=1` → `30 passed`；
  `PYTHONIOENCODING=utf-8` → `30 passed`；`LANG=zh_CN.UTF-8` **无效** → 仍 1 failed。
- **取证方法（可复用）**：给 pytest 挂一个诊断插件（`-p diag_plugin`，
  在 teardown 里把 `conn.dead_reason()/stderr_tail()/poll()` 打到 stderr）——
  真实错误详情只在**测试进程内部**可见，`--tb` 会被截断。
- **修法建议（未实施）**：`_spawn_locked` 往 env 注入 `PYTHONUTF8=1`，
  或让 MCP server 侧不依赖 locale 编码。

## [2026-09-17] `doraise=True` 也会被 `quiet=2` 吃掉 —— 语法检查静默失效
- **类型**：踩坑（**静默失效级**，最难发现的一种）
- **摔在哪**：`tools/verify.py` 的 `check_compile()`
- **现象**：语法检查对**明明有语法错误的文件**返回"合格"。要不是写了一条"故意造语法错"的
  测试，这个洞会一直在 —— 而且它每次都报"全部可编译"，看起来一切正常。
- **根因**：`py_compile.compile(path, cfile=…, doraise=True, quiet=2)` 在 **Python 3.11.15** 上
  **返回 None、不抛任何异常**（`quiet=2` 把报错吞了，连 `doraise=True` 都不再生效）。
  去掉 `quiet` 参数后行为正常（抛 `PyCompileError`）。
- **怎么办**：**不要传 `quiet`。** 更大的教训：写"检查类/守卫类"代码时，
  永远配一条**故意造错的用例**钉住它 —— "检查器永远返回通过"是最隐蔽的坏法。
- **状态**：已修，测试 `tests/test_self_maintenance.py::test_verify_compile_check_reports_syntax_error` 守护
