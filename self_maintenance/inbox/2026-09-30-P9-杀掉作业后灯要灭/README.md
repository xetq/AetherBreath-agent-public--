# P9 交付：杀掉后台任务后，编排器那盏灯要跟着灭

## 怎么激活（**只重启 AB，网关不用动**）

只改了 `agent_webui/backend/bridge.py` —— 它是 **AB 子进程的入口脚本**（由网关拉起的是新进程），
所以：

1. 界面点「⏻ 优雅关机」
2. 界面点「🟢 开机」

前端没有改动，不用刷新。

## 期望现象

1. 挂一个长后台作业（比如 `用 background 跑 sleep 300`）→ 编排器里某格亮**橙色**
2. 让 AB 调 `task_kill(job_id="jN")`
3. **期望**：那一格**在 1 秒内变灰**（`task_kill` 一返回就发终态帧）；
   最迟也不会超过前端 5 秒一次的对表
4. 顺便看 hover：那格会变成「空闲 · 上次 execute_shell」并带「失败 1」（取消算一次不顺利）

**判据（不用猜界面）**：杀掉后打开
`http://127.0.0.1:8900/api/orch` —— 被杀的那个作业**不许再出现在 `pipes` 里**。
（修复前它会以 `"status":"running","background":true` 一直赖在那里，所以前端每 5 秒
对表就把灯又点亮一次。）

## 根因一句话

`task_kill` 会把作业从登记册 **drop** 掉，而它的工具线程还在自己的取消令牌上收尾；
`/orch` 视图查不到作业时按"fail-open"**原样上报 running** —— 于是"看不见"被当成了
"可能还在跑"，灯就一直亮。

修法：**跨回合占用以登记册为准**（查得到且活着才算占用），再加一个扫尾
`_sweep_dead_background_pipes()`（发终态帧 + 出局），接在每个工具收尾处。
登记册**读不到**时仍然 fail-open（不误杀可能还在跑的作业）。

## 失败了怎么办

```
venv\Scripts\python -m pytest tests/test_orch_orange_job.py -q      # 期望 26 passed
```

若全绿而灯还是不灭，请把杀掉之后 `curl http://127.0.0.1:8900/api/orch` 的返回发我 ——
只要 `pipes` 里还有那个 `tc_id`，就是服务端视图的问题（我继续查）；
若 `pipes` 已空而界面还亮，问题在前端（那就是对表/合并逻辑）。

1. **先手动备份**：`agent_webui\backend\bridge.py`
2. **回滚**（需要你点头）：
   ```
   venv\Scripts\python self_maintenance\tools\snapshot.py rollback 20260930-011845-P9-杀掉作业后橙灯要灭_视图以登记册为准_扫尾发终态帧 --yes
   ```
   回滚后**重启 AB**。

## 一句话提醒

**被执行掉的作业，登记册里就不该有它** —— 所以"视图还报它占用"这件事本身是自相矛盾的
（一个已删除的作业，界面却显示它在占资源）。这次的教训已写进 `NOTES.md`：
**"查不到"必须分成"拿不到权威来源"（fail-open）与"权威来源说没有"（fail-closed）两种。**
