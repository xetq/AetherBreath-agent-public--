# 粒子 MV 制作

**输入一首歌，输出一支 MV。** 画面全部由代码算出来——没有素材、没有 AI 生成画面，
每一个像素都是程序画的。

这份文档是一条能走完的路：从听懂这首歌开始，到交出横竖两版 MP4 为止。
里面每一条经验都来自实际做出成品的过程，尤其是**那些让人返工一整轮的坑**。

---

## 一、全流程总览

```
一首歌 (mp3/wav/aac)
   │
   ├─ 阶段 1 · 听懂它 ──── 分离人声 → 逐句切片 → 人类核对时间码
   │                                  └→ lyrics.ts（权威时间轴）
   │
   ├─ 阶段 2 · 设计画面 ── 逐句分镜表（意象/情绪/文字动态/运镜/衔接）
   │                                  └→ 和需求方确认后才动代码
   │
   ├─ 阶段 3 · 搭骨架 ──── Remotion 工程 + 相机/粒子/文字三件套
   │                                  └→ assets/starter/ 直接拷
   │
   ├─ 阶段 4 · 逐场景实现 ─ 一次做一个场景，渲染静帧看 1:1 原图
   │
   ├─ 阶段 5 · 渲染合成 ── 分段渲染 → concat → 合音频
   │                                  └→ 横版 MP4
   │
   └─ 阶段 6 · 出竖版 ──── 换画布重新取景（不是压扁）→ 竖版 MP4
```

**一句话的节奏**：前两个阶段决定成败，中间两个阶段是体力活，最后两个阶段别偷懒做检查。

## 二、阶段 1 · 听懂这首歌

### 2.1 先分离人声

用 Demucs（或同类工具）把人声从伴奏里分出来。
这一步不是洁癖——**后面的时间轴、情绪分布、段落结构全都建立在人声轨上**。

```bash
# Demucs 在国内环境要加镜像，否则会去 huggingface 拉模型时静默空等
HF_ENDPOINT=https://hf-mirror.com python -m demucs -n htdemucs -o separated audio.wav
```

### 2.2 逐句对齐时间码（🔴 别省这一步）

**两种方式任选**，详细做法 / 完整代码 / 参数含义见 **`references/audio-align.md`**：

**方式 A · 由作者或用户提供断点** —— 最准，能问到就问。
给他三样东西：可播放的音频、带秒数刻度的**波形图**、编号的歌词全文，
请他填一张「每句起始秒数」的表。
**只要"起"不要"止"** —— 每句的结束天然等于下一句的开始，这样少填一半、也少一半错的机会。

**方式 B · 由 agent 自己分割** —— 拿到音频就能开始。
分析**人声轨**的能量包络，二值化后按**不同的静音间隙**合并，同一个算法出三档粒度：

| gap | 含义 | 用途 |
|---|---|---|
| 0.25 s | 句内停顿 | 断字点，一般不用 |
| **0.55 s** | **句子边界** | 歌词分句 ← 主要用这个 |
| 1.10 s | 段落边界 | 分主歌/副歌、找前奏与尾奏的起止 |

**但实际最好用的是组合**：算法出候选 → 按候选切片（**前后各留 0.8 秒缓冲**）→
配一张「波形 + 能量包络 + 候选切点竖线」对照图 → 交给人类听。
**人只需要做判断（"第 3 句早了"），不需要从零打点**，通常只有 2~4 句要改。

🔴 **必须重点复核的位置**：气口（换气的静音谷会被误判成句尾，往往在 −40 dB 以下）、
长音、和声、切分抢拍，以及**第一句**——前奏渐强时最容易被当成起唱。

🔴 **别把「歌词行时间码」和「人声起音」当成一回事** —— 人的习惯是把上一句的尾音和换气
算进下一句，所以歌词行边界常比人声起音**早 0.3~1 秒**。做动画要用**起音**（动作落在真正发声的瞬间），
显示歌词用**行时间码**。看到自动分析比人工标的晚一秒，先画能量曲线确认，别急着当 bug。

**为什么不能全自动**：长音、和声、气口、切分都会骗过检测器。
把这一步完全交给算法，会得到一份"看起来对"但每句都差零点几秒的时间轴，
而这个偏差在做动画时会被放大成灾难。**这是整条流程里唯一必须有人参与的环节。**

### 2.3 断句的权威来源是**原歌词的换行**

不要自己猜哪里断句。原歌词怎么分行，画面就怎么分行——那是作者的原意。
把每一句拆成 `rows: string[]`，之后排版、逐行动效都基于它。

### 2.4 产出

```ts
// src/lyrics.ts
export type LyricLineData = {
  idx: number;
  text: string;
  rows: string[];        // 语义断句（来自原歌词换行）
  start: number;         // 秒
  end: number;
  lang: 'cn' | 'en';
};
```

**这份数据是权威。** 后面所有动画都以它为准，不要在任何地方重算时间。

## 三、阶段 2 · 设计画面（最便宜也最重要的一步）

### 3.1 逐句填一张分镜表，先和需求方确认

| # | 歌词 | 主角意象 | 情绪基调 | 画面里发生什么（动词） | 镜头运动 | 与下一场的衔接 |
|---|---|---|---|---|---|---|
| 1 | … | 信封与钢笔 | 平静、克制 | 字从纸面浮起 | 从上方极缓下降 | 钢笔的长影 → 街灯 |
| 2 | … | … | … | … | … | … |

用十分钟和需求方过一遍，能省掉一整轮返工——**这张表定错了，后面所有代码都是白写。**

详细方法（怎么从歌词里抽意象、怎么避免重复、情绪怎么对应运镜）见
`references/imagery-design.md`，那里有一整套可套用的做法。

### 3.2 三条必须遵守的创意纪律

**① 每个场景一个【新】主角意象。**
一个机制好用就会忍不住反复用，但观众第三次看到同一种形式就开始走神。
开一个"已用意象"清单，写完一句记一句，主角不许重复。

**② 线索可以复用，但每次用法不同。**
光：台灯 → 街灯 → 门缝 → 车灯 → 路灯。
水：窗上雾 → 雨丝 → 水洼 → 镜面。
主角各不相同，但贯穿元素反复出现，观众才会觉得"这是同一个世界"。

**③ 每个结尾都是下一个的开头。**
不要靠淡入淡出硬接，而是让上一场里的某个东西**变形成**下一场的入口。
做到位，全片会有一口气拍下来的感觉。

### 3.3 前奏和尾奏要专门设计（新手最容易浪费的两段）

- **前奏**（常 10~20 秒、没人声）：这是建立镜头的黄金时段。
  可以极慢地推近、让灯一盏盏亮起、让天色暗下去。**别空着，也别抢戏。**
- **尾奏**（唱完之后）：让画面慢慢散掉。这段留白是给观众回味用的，
  最多放一句落款——**前面都在忍，最后给一句说透的话**。

## 四、阶段 3 · 搭骨架

`assets/starter/` 里有现成的工程地基，直接拷进新项目：

| 文件 | 职责 |
|---|---|
| `theme.ts` | 画布尺寸（横/竖可切换）、调色曲线、字体、确定性随机 |
| `lib/camera.ts` | **地基**：针孔相机投影 + 大气透视 |
| `lib/points3d.ts` | 3D 点云生成器（球/柱/盒/面/线/环/心形） |
| `lib/sceneTypes.ts` | 场景类型 + 常用相机运动（walk / orbit / dolly / pan） |
| `lib/shotTiming.ts` | 段窗口 + 交叉溶解（零硬切的机制） |
| `parts/Field3D.tsx` | 3D 粒子渲染器（投影 + 景深衰减 + 辉光） |
| `parts/Frame.tsx` | 电影黑边 / 暗角 / 胶片颗粒 |
| `text/LyricLine.tsx` | 歌词逐字动效 |

**核心抽象**：一个场景 = `cam(t) → Cam` + `layers(t) → Layer3D[]`。
`t ∈ [0,1]` 是这句内部的进度。
这样"镜头怎么动"和"画面是什么"完全解耦——改运镜不用动画面，反之亦然。

## 五、阶段 4 · 逐场景实现

**一次只做一个场景，出静帧，看 1:1 原图，修，再做下一个。**

不要一次写完 16 个场景再渲染——那样错误会乘以 16 倍。

**为什么必须看 1:1 原图**：缩放预览会伪造问题（把细小的位移/缝隙放大成"明显的错误"，
也会把真实的问题糊掉）。判断画面一律用原始尺寸。

**动效调试的顺序**：先让静帧成立 → 再看运动 → 最后调节奏。
静帧不成立的画面，动起来也不会好看。

## 六、阶段 5 · 渲染与合成

### 6.1 分段渲染

如果执行环境有超时限制（例如 120 秒），把渲染拆成**每段 600 帧**左右。

```bash
node node_modules/@remotion/cli/remotion-cli.js render <CompId> out/seg1.mp4 --frames=0-599
node node_modules/@remotion/cli/remotion-cli.js render <CompId> out/seg2.mp4 --frames=600-1199
# …
```

### 6.2 拼接 + 合音频

```bash
printf "file 'seg1.mp4'\nfile 'seg2.mp4'\n" > list.txt
ffmpeg -y -f concat -safe 0 -i list.txt -c copy silent.mp4
ffmpeg -y -i silent.mp4 -i song.wav -c:v copy -c:a aac -b:a 192k final.mp4
```

### 6.3 拼图全片自查（最快的质检方式）

用 ffmpeg 抽 16 帧拼成一张，一眼看完所有场景：

```bash
ffmpeg -y -i final.mp4 -vf "select='eq(n\,500)+eq(n\,590)+…',scale=480:-1,tile=4x4" \
       -frames:v 1 -q:v 3 sheet.jpg
```

**这是发现"哪些意象根本读不出来"最快的方式**——单看每一帧都觉得没问题，
拼在一起才发现有三句观众根本认不出画的是什么。

## 七、阶段 6 · 出竖版

因为场景是真 3D，换画布尺寸后相机是**重新取景**：横版两侧被裁掉、主体占比自动变大。
这等于换个画幅重拍一遍，而不是把画面压扁。

**好处**：同一个场景换个画幅就有新构图，某些场景竖版反而更好（纵向留白更适合星空、单人）。

**代价**：**每个尺寸都要单独看一眼**。尤其"横向并排"的构图会被裁掉——
摊开的书、横铺的桌面、并排的两个人，在竖版里都可能只剩中间一条。
遇到这种情况，给那个场景单独调焦距：

```ts
return {..., focal: IS_VERTICAL ? 660 : 940};   // 竖版拉远，让横向构完整入画
```

## 八、四条决定成败的技术判断

### 1. 做「伪 3D」，不要上 Three.js

要 3D 感，直觉是 Three.js。**这个直觉在本类项目里是错的。**

手搭几何体意味着要同时调模型、材质、灯光、透视、大气散射——缺任何一环都显廉价，
而这条管线不是几轮迭代能补齐的。实际做过一版，被评价为"像程序员画的示意图"。

真相是：**观众感受到的 3D 感，主要来自运镜、视差和景深，不是模型的真实度。**

所以：元素只保留世界坐标 `(x, y, z)`，用针孔相机投影。
相机有位置/朝向/焦距 → 推拉摇移环绕全是数学；
元素是剪影/点云（本来就不该追求写实）；
景深与大气透视让平面"立起来"。

详细推导与自检方法见 `references/projection.md`。

### 2. 用粒子「构成」物象，而不是画实心图形

实心图形出来是矢量插画，硬邦邦。粒子有体量、有呼吸、**密集处还会自己过曝发白**——
这是这套风格的质感来源。

代价：**细长复杂的形体需要足够密度才读得出来。**
块状（心形、长椅、天平）很好看；细长（手指、车身、人影）容易散成一团点。
**选意象时优先"块状、轮廓清楚"的。**

### 3. 零硬切靠「段窗口重叠」，不靠转场插件

机制只有一句话：

> 相邻两段的**时间窗口故意重叠**，前一段还在淡出时，后一段已经开始淡入。

实现是一个纯函数 `segOpacity(seg, frame) = min(淡入进度, 淡出进度)`。

**注意**：如果两段内容差异极大（一个静止 2D、一个运动 3D），
即使有溶解也会被感知成"重影"。这种接缝要把重叠缩短——
**长重叠只适合画面相近的段。**

### 4. 一切必须确定性

逐帧渲染要求每一帧都由帧号唯一决定。

**永远不要用 `Math.random()`**——否则每次渲染结果都不同、画面会闪。
用 `rng(固定种子)`，会随帧变化的动（呼吸、抖动）用 `sin(frame * 频率 + 相位)`，
相位用粒子下标算：既自然又确定。

## 九、12 个致命陷阱（速查）

**详细原理、症状、修法、代码见 `references/pitfalls.md`。**

| # | 陷阱 | 症状 | 一句话修法 |
|---|---|---|---|
| 1 | **投影旋转符号写反** | 所有"低头看"的镜头实际在"抬头"，近景场景全黑 | 自检：`pitch>0` 时正前方的点必须落在画面**下方** |
| 2 | **相机 z 放在了物体同侧** | 目标在镜头背后，画面全黑 | 物体在 `z≈0`，相机 z 必须是**负的** |
| 3 | **俯角与距离不匹配** | 推近时目标滑出画面 | 俯角用 `atan2(目标y-相机y, 距离)` **精确瞄准** |
| 4 | **规则网格在透视下产生摩尔纹** | 地面/纸面出现放射条纹 | 用**随机分布**的点 |
| 5 | **整层位移做下雨** | 雨像"同一段动画循环播放" | 每滴雨要有**自己的高度与速度相位** |
| 6 | **`scale = focal/depth` 在近处爆炸** | 出现贯穿屏幕的巨大黑影 | 限制尺寸上限；跳过 `depth` 过小的元素 |
| 7 | **用线条勾勒人形** | 出来是"机器人" | 人形用**实心剪影** |
| 8 | **手的掌心画太大** | 粒子聚成一团，看不出是手 | 掌心小、手指细长，且从掌心**中心**起笔 |
| 9 | **相机绕原点转却不看向原点** | 主体在镜头背后 | 绕圈时 `yaw = 角度 + π` |
| 10 | **换了图层忘了改引用** | 以为删掉的旧场景还在播 | 调度表是唯一入口，改完**打印出来读一遍** |
| 11 | **帧内用了 `Math.random()`** | 每次渲染都不同 / 画面闪烁 | 用 `rng(seed)` |
| 12 | **Composition id 带下划线** | Remotion 直接报错 | id 只允许 `a-z A-Z 0-9 - 和 CJK` |

**通用心法**：画面全黑时，**先怀疑相机，不要怀疑素材**。
绝大多数"什么都没有"是相机位置或朝向错了，而不是粒子没生成。

## 十、歌词与文字

- **字体**：中文衬线（宋体系）有书写感，适合"信 / 离别 / 思念"这类主题。
  系统宋体在 Chromium 里能直接解析，**不需要嵌字体文件**。
  大字号下宋体笔画偏瘦，若要更有设计感可换思源宋体。
- **对齐**：按语义断句，标点不落行首，中英混排分别处理字距。
- **动效**：逐字浮起（每字错开 2~4 帧）+ 轻微呼吸（每字相位不同）+ **暗晕**。
  暗晕不是可选项——亮背景上白字会糊成一团。
- **让文字跟着画面变**：例如灯闪烁时，字色在冷↔暖之间同步变化。
  这是"动画跟着歌词走"最省力也最有效的表达。
- **字幕位置**：横版约在画面下方 75% 处；竖版要下移并**缩小字号**
  （1080 宽装不下 80px 的 11 字长句）。

## 十一、交付

一支合格的成品应该包含：

- **横版 + 竖版**各一份（`Composition` 加一个即可，但取景要各自校准）
- **片头信息**（竖版建议加）：在前奏没人声的那段放"制作 / 生成方式 / 配乐来源"——
  那几秒画面最空，正好把该交代的交代掉，不侵占歌词任何一秒
- **片尾落款**：一句把这支片子的意思**说明白**的话（前面都在忍，最后给一句）
- **可运行的工程文件**：用户可能只想改其中一句，模块化结构让他能只重渲那一句
