# 把歌词切到时间轴上 —— 两种方式 + 一种组合

> 这是整条流程里**唯一无法全自动**的一步。
> 后面每个场景的起止、每段动画的节奏都建立在这份数据上，
> 所以它错半拍，全片就散架。
>
> 这里给两种做法，以及实际最好用的组合。

---

## 方式一 · 由作者/用户提供断点（最准，优先用）

写歌的人（或拿得到准确信息的人）最清楚句子在哪里起、哪里收。
**能问到就问，别自己猜。**

### 怎么让对方打点

不要只说"给我每句的时间"——那样得到的数据通常没法用。给三样东西：

1. **一份可直接播放的音频**（最好就是 MV 要用的那一段，别让他从三分钟的整曲里换算）
2. **一张波形图**（标好秒数刻度）—— 让人能对着波形说"这里起"
3. **歌词全文，按行编号**（和波形图并排）

然后请他填一张表：

| # | 歌词 | 起（秒） |
|---|---|---|
| 1 | … | 15.49 |
| 2 | … | 18.15 |

**只要"起"，不要"止"。** 因为每句的结束天然等于下一句的开始，
只需要额外提供最后一个收尾时间（末尾那句的结束，或整段的结束）。
这样能少填一半，也少一半错的机会。

### 收到之后要做的三件事

1. **校验单调性**：时间必须严格递增，且每句时长不能为负
2. **校验合理性**：用自动分析的能量包络对一遍（见方式二），
   如果有人打错了一位数（比如 18.15 写成 81.15），这一步能立刻抓到
3. **补齐两处边界**：**前奏结束**（第一句起唱）和**尾奏开始**（最后一句收声）——
   这两个点决定了前奏和尾奏的长度，一定要单独确认

### 一个真实例子

有一版的断点由需求方逐句手工切好，我只做了两处**实测修正**：

- 第 1 句 **15.00 → 15.49**：前奏是纯音乐，真正起唱在 15.49，
  人耳容易把伴奏里的某个重音听成"开始唱"
- 最后一句 **74.61 → 76.00**：这里有一个 **−46 dB 的换气谷**，
  而正确的位置应该在谷底之后。这类"气口"是最容易切错的地方

**教训**：即使是最准的人工断点，也值得用算法复核一遍——
不是怀疑人，而是**人对边界的判断标准**（听感）和**画面的需求**（动作要落在哪个瞬间）
常常差那么零点几秒。

## 方式二 · 由 agent 自动分割（拿到音频就能开始）

核心思路：**人声轨的能量包络 → 二值化 → 按不同的静音间隙合并，得到不同粒度的分段。**

### 为什么要先分离人声

直接用混音做能量分析会被鼓和贝斯骗到——副歌的鼓点很强，但那里可能是换气。
**先把人声分离出来**（Demucs 或同类工具），分析才干净。

```bash
# 国内环境要加镜像，否则拉模型时会静默空等（看起来在跑，其实在等超时）
HF_ENDPOINT=https://hf-mirror.com python -m demucs -n htdemucs -o separated song.wav
```

### 算法（零依赖，标准库 + numpy 就够）

```python
import numpy as np, wave

def load_mono(path):
    with wave.open(path, "rb") as w:
        sr, n, ch, sw = w.getframerate(), w.getnframes(), w.getnchannels(), w.getsampwidth()
        raw = w.readframes(n)
    if sw == 2:
        x = np.frombuffer(raw, dtype="<i2").astype(np.float32) / 32768.0
    elif sw == 4:
        x = np.frombuffer(raw, dtype="<i4").astype(np.float32) / 2147483648.0
    else:
        raise ValueError("unsupported sampwidth %d" % sw)
    if ch > 1:
        x = x.reshape(-1, ch).mean(axis=1)     # 混单声道
    return sr, x

sr, v = load_mono("separated/htdemucs/vocals.wav")

# ① 帧化：每 10 ms 一帧，每帧 40 ms 的窗
hop, win = int(sr * 0.01), int(sr * 0.04)
frames = np.lib.stride_tricks.sliding_window_view(v, win)[::hop]

# ② 每帧的 RMS → dB
db = 20 * np.log10(np.sqrt((frames ** 2).mean(axis=1)) + 1e-9)
times = np.arange(len(db)) * hop / sr

# ③ 阈值：相对「响亮部分」低 22 dB —— 比绝对阈值稳健得多
thr = np.percentile(db, 90) - 22
voiced = db > thr

# ④ 取连续的发声片段
segs, i = [], 0
while i < len(voiced):
    if voiced[i]:
        j = i
        while j < len(voiced) and voiced[j]:
            j += 1
        segs.append([times[i], times[j - 1]])
        i = j
    else:
        i += 1

# ⑤ 按不同的静音间隙合并 —— 同一个算法，三档粒度
def merge(sg, gap, minlen=0.30):
    out = []
    for s in sg:
        if out and s[0] - out[-1][1] < gap:
            out[-1][1] = s[1]
        else:
            out.append(list(s))
    return [tuple(x) for x in out if x[1] - x[0] >= minlen]

for gap, tag in [(0.25, "句内停顿"), (0.55, "句子边界"), (1.10, "段落边界")]:
    m = merge([list(s) for s in segs], gap)
    print(f"--- gap={gap}s ({tag}) -> {len(m)} 段 ---")
    for k, (a, b) in enumerate(m, 1):
        print(f"  {k:2d} {a:7.2f} -> {b:7.2f}  ({b - a:.2f}s)")
```

### 三个 gap 值分别是什么

**这是这套方法最有用的一点** —— 同一个能量包络，换一个合并间隙就得到不同层级的结构：

| gap | 含义 | 用途 |
|---|---|---|
| **0.25 s** | 句内停顿（词与词之间） | 找断字点，一般不用 |
| **0.55 s** | **句子边界** ← 主要用这个 | 歌词分句 |
| **1.10 s** | 段落边界 | 找主歌/副歌的分界、前奏与尾奏的起止 |

**用法建议**：先用 `gap=1.10` 把整首歌切成大段落（前奏 / 主歌 / 副歌 / 间奏），
再用 `gap=0.55` 在每个段落内部切句子。两层结构一次拿到。

### 参数怎么调

- **阈值 −22 dB**：相对响度的 90 分位。相对阈值比绝对阈值稳健——不同歌的录音电平差很多
- **最小段长 0.30 s**：滤掉咔哒声和口水音造成的碎片
- **帧长 40 ms / 步长 10 ms**：40 ms 足够覆盖一个音节，10 ms 的定位精度对人耳来说够用

## 方式三 · 实际最好用的：算法给候选 + 人校正（推荐）

单独用前两种都有短板：
- 纯自动：气口、长音、和声会骗过算法，误差常在 0.2~0.5 秒
- 纯人工：慢，而且人会累，后段容易越来越敷衍

**组合起来，人只需要做「判断」而不需要做「打点」：**

### 流程

1. **自动分析** → 出候选时间轴（方式二的代码）
2. **按候选切片**：每句切一个 wav，**前后各留 0.8 秒缓冲**
   （留缓冲是关键：让人能听到句尾是怎么收的、下一句是怎么进来的）
3. **同时出一张对照图**：波形 + 能量包络 + 候选切点竖线 + 秒数刻度
   —— 把音频和"我标的线"放在同一张图上，人一眼就能看出哪里歪了
4. **交给人类听**，只需要回答"第 N 句早了/晚了，改成 X"
5. **只改那几句的时间**，其余不动

### 为什么这样最省力

- 人不需要从零打点，只需要**否定**（"这句早了"）
- 有缓冲的切片 + 波形图，让判断变得很快（不用来回拖进度条）
- 差的通常只有 2~4 句，其余自动结果直接可用

### 校验清单：这几类位置一定要重点听

| 位置 | 为什么会错 |
|---|---|
| **换气 / 气口** | 句中换气的静音谷会被误判成句尾（找**局部极小值**，往往在 −40 dB 以下） |
| **长音** | 一个字拖很久，算法会把这一整段算成一句，实际后面还有词 |
| **和声 / 伴唱** | 人声分离后主唱与和声混在一起，能量持续不断，切不出边界 |
| **切分 / 抢拍** | 歌手故意提前半拍进，人耳觉得"到了"，算法还在等能量上升 |
| **第一句** | 前奏伴奏渐强时容易被当成起唱（这是最常见的错误） |
| **最后一句** | 尾音拖长、渐弱，收声点很难自动判断 |

## 🔴 一个容易被误判成 bug 的系统性差异

**「歌词行的时间码」和「人声真正起音」不是一回事，通常差 0.3~1 秒。**

实测数据（某首歌第 1→2 句之间，人声轨的能量曲线）：

| 时间 | 能量 | 实际发生的事 |
|---|---|---|
| 17.0 – 18.0 s | −12 ~ −24 dB | 第 1 句在唱 |
| 18.4 – 19.0 s | **−47 ~ −64 dB** | **真的没有人声**（换气） |
| 19.1 s | −34.6 dB | 第 2 句起唱 |

而人工标出的歌词行边界是 **18.15 s** —— 比人声起音早了将近 1 秒。

**两个都对，只是定义不同**：

| | 测的是什么 | 应该用在哪 |
|---|---|---|
| **歌词行时间码** | 这句歌词占用的**时间段**（人的习惯：把上一句的尾音和换气算进下一句） | 文字显示时段、分镜划分 |
| **人声起音** | 嗓子**真正发出声音**的瞬间 | **动画动作的落点** |

**所以**：
- 看到"自动分析的结果比人工标的晚了快 1 秒"时，**先别当成 bug**。
  用 `make_chart.py` 把能量曲线画出来看一眼——那 1 秒里多半是真的没人声。
- 做动画时**用起音**（动作要落在真正发声的瞬间，早 1 秒就会"口型对不上"）
- 显示歌词时**用歌词行时间码**（观众读的是句子，不是音素）

这条差异是这套工具最容易引起误会的地方，写在这里以免重复踩。

## 定稿之后

产出这样一份数据，**它是唯一权威**，后面所有环节都读它、不重算：

```ts
export type LyricLineData = {
  idx: number;
  text: string;
  rows: string[];      // 语义断句（权威来源：原歌词的换行）
  start: number;       // 秒
  end: number;
  lang: 'cn' | 'en';
};
```

顺带把它转成帧号（`frame = round(sec * fps)`）——Remotion 里一切以帧为单位。

**再强调一次**：断句（`rows`）不要自己猜，用**原歌词的换行**。
那是作者的原意，也决定了画面上文字怎么折行。
